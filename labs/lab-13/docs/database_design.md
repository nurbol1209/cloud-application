# Проектирование базы данных Cloud Application

## Назначение

База данных должна хранить сведения о типах облачных сервисов и о самих
сервисах, обеспечивая ссылочную целостность.

## Сущности

### ServiceType — тип сервиса

| Поле | Тип | Ограничения | Назначение |
| --- | --- | --- | --- |
| `id` | `INTEGER` | PK | идентификатор типа |
| `name` | `VARCHAR(50)` | NOT NULL, UNIQUE | название типа |
| `description` | `VARCHAR(255)` | NULL | описание |

Примеры типов: `application`, `database`, `monitoring`.

### Service — облачный сервис

| Поле | Тип | Ограничения | Назначение |
| --- | --- | --- | --- |
| `id` | `INTEGER` | PK | идентификатор сервиса |
| `name` | `VARCHAR(100)` | NOT NULL | название сервиса |
| `type_id` | `INTEGER` | NOT NULL, FK → `service_types.id` | тип сервиса |
| `status` | `VARCHAR(20)` | NOT NULL | состояние |
| `description` | `VARCHAR(255)` | NULL | описание |
| `endpoint_url` | `VARCHAR(255)` | NULL | адрес сервиса |

Допустимые состояния: `running`, `maintenance`, `stopped`.

## Связь

```
service_types 1 ────────── N services
                type_id (FK)
```

Один тип может использоваться многими сервисами; каждый сервис относится
ровно к одному существующему типу.

## ER-диаграмма

```
┌────────────────────┐          ┌──────────────────────────┐
│    service_types   │          │         services         │
├────────────────────┤          ├──────────────────────────┤
│ id           PK    │ 1      N │ id                PK     │
│ name         UQ    │──────────│ type_id           FK     │
│ description        │          │ name                     │
└────────────────────┘          │ status                   │
                                │ description              │
                                │ endpoint_url             │
                                └──────────────────────────┘
```

## Правила целостности

1. Идентификаторы уникальны (PRIMARY KEY).
2. Название типа сервиса не должно дублироваться (UNIQUE).
3. Сервис не может ссылаться на несуществующий тип (FOREIGN KEY).
4. Обязательные поля не могут быть `NULL` (NOT NULL).
5. Состояние сервиса ограничено допустимыми значениями (CHECK — ЛР № 17).

## Самостоятельное задание: история состояний

Дополнительная сущность `ServiceStatusHistory`:

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | `INTEGER` | PK |
| `service_id` | `INTEGER` | NOT NULL, FK → `services.id` |
| `status` | `VARCHAR(20)` | NOT NULL |
| `changed_at` | `TIMESTAMP WITH TIME ZONE` | NOT NULL, DEFAULT now() |

Связь: `services 1 ────────── N service_status_history`.

```
┌──────────────┐        ┌────────────────────────┐
│   services   │ 1    N │ service_status_history │
│ id      PK   │────────│ service_id         FK  │
└──────────────┘        │ status                 │
                        │ changed_at             │
                        └────────────────────────┘
```

История позволяет сохранять все изменения состояния сервиса и строить отчёты
о времени работы и простоях.

## Вывод

Модель нормализована: тип сервиса вынесен в справочник, а сервис хранит только
ссылку на него. Это устраняет дублирование названий типов и обеспечивает
целостность данных.
