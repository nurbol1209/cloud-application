# Лабораторная работа № 34. Анализ и оптимизация программного компонента

## Цель

Выполнить измеримый анализ производительности компонента Cloud
Application: подготовить воспроизводимый сценарий обработки данных,
получить базовые измерения, профилировать реализацию средствами
`cProfile`/`pstats`, определить фактическое узкое место, заменить
повторный линейный поиск словарём, подтвердить функциональную
эквивалентность и количественно оценить эффект повторным измерением
в тех же условиях.

## 1. От предположения к измерению

Оптимизация «на глаз» недопустима: короткий код не всегда быстрее,
а современная конструкция языка сама по себе не гарантирует выигрыша.
Использован цикл:

```text
исходное состояние
        |
        v
фиксированный набор данных
        |
        v
измерение (5 запусков) --> digest результата
        |
        v
cProfile --> pstats --> измеренное узкое место
        |
        v
изменение только выбранного участка
        |
        v
совпадение digest --> повторное измерение --> speedup / reduction
```

Исследуемый компонент — `build_service_report()` в
[app/services/reporting.py](app/services/reporting.py). Он превращает
сервисы в отчёт, подставляя имя типа вместо `type_id`. Именно поиск
имени типа и стал предметом оптимизации.

## 2. Исходный компонент

Исходная реализация (до оптимизации):

```python
def build_service_report(
    services: list[dict],
    service_types: list[dict],
) -> list[dict]:
    report = []
    for service in services:
        type_name = "unknown"
        for service_type in service_types:
            if service_type["id"] == service["type_id"]:
                type_name = service_type["name"]
                break
        report.append(
            {
                "id": service["id"],
                "name": service["name"],
                "status": service["status"],
                "type": type_name,
            }
        )
    return report
```

Реализация функционально корректна. Недостаток не в результате, а в
объёме повторяющейся работы: для каждого сервиса список типов
просматривается заново.

## 3. Воспроизводимый performance-сценарий

Файл [scripts/profile_service_report.py](scripts/profile_service_report.py).

Параметры:

| Параметр | Значение |
| --- | --- |
| `SERVICE_COUNT` | 20 000 |
| `TYPE_COUNT` | 200 |
| `REPEATS` | 5 |

Ключевые фрагменты:

```python
STATUSES = ("running", "maintenance", "stopped")

service_types = [
    {"id": type_id, "name": f"type-{type_id}"}
    for type_id in range(1, TYPE_COUNT + 1)
]

services = [
    {
        "id": service_id,
        "name": f"service-{service_id}",
        "type_id": ((service_id * 37) % TYPE_COUNT) + 1,
        "status": statuses[service_id % len(statuses)],
    }
    for service_id in range(1, SERVICE_COUNT + 1)
]
```

Каждое измерение:

```python
started = time.perf_counter()
report = build_service_report(services, service_types)
elapsed = time.perf_counter() - started
```

Итоговая статистика: `statistics.mean(times)`, `min(times)`.

### Детерминированность

`random` не используется. `type_id` вычисляется по фиксированной
формуле `((service_id * 37) % 200) + 1`, статус — по индексу
`service_id % 3`, порядок записей задан диапазоном. Поэтому при
каждом запуске совпадают число сервисов, число типов, распределение
`type_id`, статусы, порядок записей и итоговый digest.

### Digest как проверка эквивалентности

```python
payload = json.dumps(report, sort_keys=True, ensure_ascii=False).encode("utf-8")
return hashlib.sha256(payload).hexdigest()
```

SHA-256 здесь не средство безопасности, а компактный способ сравнить
20 000 записей без вывода их в консоль. Совпадение digest означает
совпадение данных и порядка записей.

Для сценария 20 000 × 200 точное число сравнений линейного поиска:
2 010 000 (средняя длина просмотра 100,5 элемента, максимум 200).

`ServiceType` по `id` внутри цикла обработки каждого сервиса.

`type_id → name`, то каждый сервис будет выполнять одно обращение по
ключу вместо просмотра списка. Функциональный результат не изменится.

## 6. Оптимизированная реализация

```python
def build_service_report(
    services: list[dict],
    service_types: list[dict],
) -> list[dict]:
    types_by_id = {item["id"]: item["name"] for item in service_types}

    report = []
    for service in services:
        type_name = types_by_id.get(service["type_id"], "unknown")
        report.append(
            {
                "id": service["id"],
                "name": service["name"],
                "status": service["status"],
                "type": type_name,
            }
        )
    return report
```

### Сравнение алгоритмов

```text
До:
  Service 1 --> просмотр ServiceType 1..200 --> найдено имя
  Service 2 --> просмотр ServiceType 1..200 --> найдено имя
  ...
  20 000 раз

После:
  ServiceType 1..200 --> один раз создаётся types_by_id
  Service 1 --> types_by_id[type_id]
  Service 2 --> types_by_id[type_id]
  ...
  20 000 обращений по ключу
```

Цена оптимизации — дополнительная память под словарь (200 элементов
в исследованной конфигурации) и один проход по справочнику на вызов
функции. Это осознанный компромисс «время–память»: память расходуется,
чтобы убрать массовые повторные поиски.


## 10. Ограничения benchmark

Локальный сценарий сравнивает поведение конкретного алгоритма и не
отвечает на вопросы эксплуатации: сколько запросов в секунду
выдерживает система, как ведёт себя приложение при 100 одновременных
клиентах, сколько CPU потребляет контейнер в течение часа, как
меняется latency PostgreSQL под нагрузкой, что происходит при
деградации сети. Это задачи нагрузочного тестирования и мониторинга
РО 3.2, а не микробенчмарка.

### Анализ компромисса «время–память»

1. Оптимизированная версия создаёт дополнительный словарь
   `types_by_id`.
2. Дополнительно расходуется оперативная память: 200 пар
   `id → name` на каждый вызов функции.
3. Расход приемлем: справочник мал по сравнению с 20 000 записей
   отчёта, а экономия времени составляет 94.72%.
4. Построение словаря не дало бы заметного преимущества, если бы
   сервисов было мало, поиск выполнялся один раз или справочник
   постоянно менялся и требовал перестройки.
5. Если значение нужно найти один раз, полный проход по списку из
   `m` элементов сопоставим с построением словаря из `m` элементов:
   подготовка структуры не окупается.
6. Оптимизация зависит от характера использования данных: словарь
   выгоден при многократном поиске по ключу, список — при однократном
   просмотре или когда важен порядок элементов.

## 12. Ответы на контрольные вопросы

1. **Оптимизация компонента** — изменение реализации, уменьшающее
   расход ресурсов при сохранении ожидаемого результата.
2. **Почему начинать с измерения** — интуиция часто указывает не на
   тот участок; только профиль показывает фактическое распределение
   времени.
3. **Узкое место** — участок, вносящий основную долю времени или
   ресурсов в исследуемом сценарии.
4. **Почему нельзя по внешнему виду** — длина и «современность» кода
   не определяют число операций и стоимость вложенных вызовов.
5. **`time.perf_counter()`** — монотонный таймер с высоким
   разрешением для измерения интервалов.
6. **Несколько измерений** — одно измерение подвержено случайным
   колебаниям из-за ОС, CPU и фоновой нагрузки.
7. **Одинаковый набор данных** — иначе сравниваются разные объёмы и
   распределения, и разница времени не относится к оптимизации.
8. **`cProfile`** — встроенный профайлер, собирающий статистику
   вызовов и времени выполнения.
9. **`pstats`** — модуль чтения и сортировки сохранённого профиля.
10. **`ncalls`** — сколько раз функция была вызвана.
11. **`tottime`** — время внутри функции без времени вложенных вызовов.
12. **`cumtime`** — суммарное время функции вместе с вложенными
    вызовами.
13. **Польза `cumtime`** — позволяет быстро найти функцию, под которой
    сосредоточена основная стоимость.
14. **Исследуемый компонент** — `build_service_report()` в
    `app/services/reporting.py`.
15. **Результат функции** — список записей отчёта с `id`, `name`,
    `status` и именем типа вместо `type_id`.
16. **Недостаток исходного алгоритма** — повторный полный просмотр
    справочника типов для каждого сервиса.
17. **Почему много сравнений** — вложенный цикл даёт порядка
    `SERVICE_COUNT × TYPE_COUNT` сравнений.
18. **`types_by_id`** — словарь, построенный один раз:
    `id → name` для всех типов.
19. **Почему ключ подходит** — доступ по ключу не зависит от позиции
    элемента и выполняется за одну операцию.
20. **Дополнительный ресурс** — память под словарь.
21. **Компромисс «время–память»** — сознательный расход памяти ради
    сокращения времени выполнения.
22. **SHA-256 digest** — компактное стабильное представление отчёта
    для сравнения результата.
23. **Почему digest должен совпадать** — иначе реализации возвращают
    разные данные и сравнивать их скорость бессмысленно.
24. **Успешна ли оптимизация при другом результате** — нет;
    изменился функциональный результат, а не только производительность.
25. **Функциональная эквивалентность** — одинаковые выходные данные
    при одинаковых входных.
26. **Speedup** — `T_before / T_after`.
27. **Процент уменьшения** — `(T_before - T_after) / T_before × 100%`.
28. **Почему нельзя переносить примерные числа** — время зависит от
    процессора, версии Python, фоновой нагрузки и режима питания.
29. **Зачем сохраняются `.prof`** — чтобы повторно исследовать
    статистику без повторного запуска и сравнить до/после.
30. **Что сравнивать в профилях** — общее время, `ncalls`, `tottime`
    и `cumtime` исследуемой функции, а также число повторных операций.
31. **Почему словарь создаётся один раз** — справочник не меняется
    между сервисами; повторное построение вернуло бы лишнюю работу.
32. **Всегда ли словарь быстрее** — нет; выигрыш зависит от числа
    повторных поисков, размера справочника и стоимости построения.
33. **Когда построение неоправданно** — при однократном поиске, малом
    числе элементов или частой перестройке справочника.
34. **Почему рост `TYPE_COUNT` деградирует линейный вариант** — растёт
    средняя длина просмотра списка, а значит и число сравнений.
35. **Зачем Ruff после оптимизации** — убедиться, что изменение не
    нарушило принятые правила и форматирование проекта.
36. **Зачем `compileall`** — проверить, что изменённые модули
    компилируются и не содержат синтаксических ошибок.
37. **Зачем проверять Git diff** — убедиться, что изменение
    локализовано и не содержит постороннего рефакторинга или секретов.
38. **Зачем smoke-проверка** — оптимизация компонента не должна
    нарушить работу всего приложения и межсервисного сценария.
39. **Benchmark и нагрузочное тестирование** — benchmark сравнивает
    алгоритмы на фиксированных данных, нагрузочное тестирование
    исследует поведение системы под конкурентной нагрузкой.
40. **Статический анализ и профилирование** — первый проверяет код
    без запуска, второй измеряет фактическое выполнение.
41. **Debugger и profiler** — debugger останавливает выполнение и
    показывает состояние, profiler собирает статистику без остановки
    на каждом шаге.
42. **Профилирование до и после** — чтобы доказать, что изменилось
    именно выбранное узкое место, а не что-то ещё.

## 13. Git

```bash
git switch -c feature/optimize-service-report
python scripts/profile_service_report.py

# ... оптимизация ...
python scripts/profile_service_report.py
python -m cProfile -o profile_after.prof scripts/profile_service_report.py
./scripts/check_quality.ps1
python -m compileall -q app scripts
git add app/services/reporting.py scripts/profile_service_report.py \
  scripts/benchmark_scaling.py scripts/benchmark_dict_variants.py \
  compose.yaml Dockerfile scripts/check_compose_config.py .gitignore \
  docs README.md

```

Файлы `profile_before.prof` и `profile_after.prof` — локальные
диагностические артефакты, в Git не добавляются (`*.prof` в
`.gitignore`).
